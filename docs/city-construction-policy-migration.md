# 城市建设策略与历史迁移

## 新城的可用入口

治理配置 `2026-09-26.pending.3` 中，全新城市仅中心众议院（`commons`）初始建成。包括外环众议院（`commons_outer`）在内的其余命名建筑须完成筹建；未建成建筑的模型、地皮、名称、地图入口和点击入口同步隐藏。个人默认解锁与管理员访问覆盖都不能代替城市建设完成状态。

居民可通过中心众议院参与共同募捐。打开治理面板不需要先付费解锁或参观众议院：治理入口先于建筑参观流程处理。顶栏「档案」仍可打开统计与成就面板，统计面板提供纪念碑入口；这些界面入口不要求 `stats` 或 `elevator` 实体建筑建成，也不会把这两栋建筑提前建成。控制台调试毁坏仍按[建筑毁坏规则](building-destruction.md)禁用对应入口，包括众议院；显式修复后恢复，建设初始策略不绕过调试毁坏状态。

其他建筑对应的剧情、商店和体验在建成后开放。`archive`、`newsstand`、`guesthouse`、`mall_south`、`mall_west` 和 `research` 是有意设置为筹建后开放的剧情入口，必须通过众议院完成相应建设项目。`litreview`、`teahouse_outer` 原有的剧情或访问限制仍然生效；建成不等同于取消所有访问条件。

NPC 任务仍可接受；如果首阶段要求访问尚未建成的建筑，接受前后的对话会说明须先在众议院共同募捐。剧情指引点击未建成的报摊或客栈时显示同类提示，不把镜头移向隐藏建筑；建设完成后恢复原导航和任务推进。

建设状态不可用时，客户端只沿用当前页面已经确认的建设结果。冷启动若取得配置（包括会话中缓存的配置）但未取得可信状态，则仅显示配置中的初始建筑，其余建设项目保持隐藏，直到服务端确认；不会从浏览器存储恢复旧的建设状态。若配置请求也失败且没有可用的配置或当前页面状态，客户端无法识别建设项目，保留原有本地场景作为降级展示；这不是服务端确认的已建成城市，也不会改变服务器的访问与扣款校验。

治理面板在配置或进度请求进行中显示加载提示；请求结束仍无匹配数据时才显示失败与重试。不会用新配置搭配旧进度提供支付操作，原操作错误与未确认支付收据也不会被加载过程清除。

地图打开期间，建设广播会立即更新图标、搜索结果和可用入口；背景场景截图在重新打开地图时更新，避免连续广播反复创建截图渲染上下文。昼夜主题切换会刷新已打开的地图截图，同时保留搜索、选择和焦点。

## 保持原有经济规则

每位新居民有 1,200 金币，公共建筑每项需要 3,000 金币。没有其他支出时，三位居民可分别捐献 1,200、1,200、600 金币完成首栋建筑。现有每日、一次性与可重复领取奖励提供物品，没有可反复领取的金币来源。

道路与绿化中的公共工程价格较低，新居民可独自完成部分项目，例如 300 金币的绿道座椅或 450 金币的东北角路灯。治理列表提供分类跳转，可直接查看这些项目；“单人无法建成首栋公共建筑”不意味着无法参与建设或完成公共工程。

成就达成时，客户端的进度控制器自动发出成就同步，服务端校验可验证条件并通过奖励记录保证只发放一次；居民无需打开统计或成就面板、点击领取按钮。可验证的金币成就包括落籍、首次访问建筑、访问 5/10 栋建筑和解锁 3 栋建筑。仅由客户端声明、服务端无法验证的成就不会凭奖励目录中的数字发放金币。相关实现见 `apps/web/src/city/progression/progressionController.ts`、`apps/web/src/adapters/ui/cloudProgressionController.ts`、`apps/server/src/progression.ts` 和 `apps/server/src/db.ts`。

单个新居民在没有额外金币来源时仍不能独自建成首栋公共建筑。建筑访问前置的支线、剧情和相关成就需要共同募捐后开放。本次不加入首栋折扣或启动补助，维持“仅中心众议院初始建成”和现有持久化价格协议；单人兜底属于后续独立经济设计。未来若修改已持久化的建设价格或配置，须另行提供显式对账迁移。

## 历史城市的显式对账

升级提示：已有城市中，过去仍显示模型的未完成筹建项目也会隐藏；这些建筑的剧情、商店和公共交互入口将等到建设完成后开放。升级不会清空已保存的个人任务、住房关系、金币或已筹金额；旧城保留哪些已建建筑由下面的对账规则决定，不因模型曾经可见而自动赠送建设进度。居民可在初始已建成的中心众议院查看和资助待建项目。

升级和备份恢复共用事务内迁移：读取旧配置、计算保留建筑和后续写入属于同一事务，任一步失败会回滚整个迁移或恢复。旧配置的初始建筑转换为已完成项目；旧项目的 ID、定义、已筹资金额、个人装饰、居民余额和 `city_operations` 幂等记录保持不变。

合法旧配置不会同时把同一建筑列为初始建筑和筹建项目。如果损坏或手工修改的备份为待保留初始建筑注入了部分筹资记录，迁移会拒绝并回滚，要求显式对账，不会自动补齐金额。

只有治理账本出现前的已有居民数据库才使用冻结的 `LEGACY_INITIAL_BUILDINGS` 历史初始清单，并从 `LEGACY_UNLOCK_PRESERVATION_BUILDINGS` 许可清单读取旧解锁。许可清单内曾被居民解锁的建筑有意保留为公共已建成项目，不扣款、不生成虚构捐款记录。空数据库使用新城初始策略；已有治理账本的版本升级不再把个人解锁或管理员访问覆盖换算成建设进度，未来新增建筑也不能沿用这次兼容规则。此过程不要求 Schema 5 备份包含 `world_config` 表。

本开发分支中的未发布中间版本 `.pending.2` 将先前遗漏的照相馆（`photostudio`）纳入服务端目录。兼容规则固定针对这个建筑 ID：保存的旧配置缺少照相馆项目、且旧账本没有该项目行时，保留其原本可见的照相馆并显式补为已建项目。判断依据是保存的配置与账本，而非版本名称清单。治理账本出现前的已有城市也保留照相馆，新城市则需要筹建。此例外不能为未来新增建筑自动赠送建设进度。

照相馆同时加入个人解锁目录，由 WebSocket `hello.catalog.buildingPrices` 和 `hello.catalog.buildingUnlockable` 对外提供；其个人解锁价格与现有建筑一致，仍为 0 金币。个人解锁只在城市完成建设后生效，不替代照相馆的 3,000 金币公共筹建，也不改变迁移时的余额、筹资或支付收据。

`.pending.3` 合入 `.areas.2` 的区域布局修正：保留 4 个区域、88 个新增地块的 ID、顺序和装饰选项，将原始布局中侵占道路、环道或海滩的位置移到已核验的安全位置，并调整两个区域公共项目的装饰位置。`cityAreaLayoutMigration.ts` 只接受与冻结旧布局逐项相符的记录，目标几何由固定哈希校验；任意再次移动或未知旧定义仍拒绝迁移。原有 13 个地块、已筹金额、建成状态、装饰归属、居民余额和付款收据不变，已购买地块随原 ID 搬迁且不再次扣款。启动和恢复均在既有事务内对账，失败整体回滚；详见[区域装饰账本迁移](city-area-migration.md)。

覆盖的历史配置包括 `2026-09-19.1`、`2026-09-25.areas.1` 和 `2026-09-26.areas.2`；前一区域版本同时核对原始布局与建筑策略迁移，后一区域版本保留已纠正的布局、只迁移建筑策略。`2026-09-25.pending.1` 仅在本开发分支中出现、尚未发布，对它的恢复测试是防御性兼容。照相馆对账不扣金币、不改旧项目、不新增支付收据。迁移实现位于 `apps/server/src/cityGovernanceMigration.ts` 和 `apps/server/src/cityGovernanceSchema.ts`；新城、历史配置、Schema 5 恢复和事务回滚由 `apps/server/tests/city-governance.mjs` 覆盖，常规集成套件还在准备旧城前验证新城图书馆访问被拒绝。

## Schema 7 投票账本

Schema 7 通过 `cityVotingSchema.ts` 增量创建 `city_votes` 和 `city_vote_operations`。前者以居民和项目为联合主键，保证每位居民每项建筑最多一票；后者以居民和请求编号为联合主键，将请求永久绑定到原项目与配置版本。免费投票不扣金币，也不替代项目的募捐和建成规则。对同一建筑换请求编号重复投票仍保存原参数收据，防止这个编号以后被用于其他项目；容量治理不能按时间直接删除在线投票收据。

启动、进程内备份恢复及离线恢复共用 `initializeCityGovernance` 中的事务内初始化。恢复 Schema 5/6 旧备份时新增空投票账本，保留建设定义、已筹金额、建成状态、装饰归属、居民余额与 `city_operations`；恢复已有 Schema 7 备份时保留投票和投票收据。离线恢复会写入当前 `user_version` 后再启动服务，任一步失败沿用既有恢复回滚机制。备份恢复后的新城市 epoch 使客户端重新读取个人投票记录，不能沿用恢复前的确认结果。相关覆盖见 `apps/server/tests/restore.mjs` 和 `apps/server/tests/city-governance.mjs`。
